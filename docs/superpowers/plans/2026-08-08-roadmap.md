# DragOS Long-Term Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sequence every planned subsystem (APIC, storage, SMP, syscall completeness, priority scheduling, Linux KPI) into dependency-ordered phases that each leave the kernel booting green.

**Architecture:** Phases are ordered by *prerequisite relationships*, not by glamour. APIC precedes SMP (LAPIC+IPI are the SMP substrate). Storage needs PCI enumeration before any driver. Priority scheduling is a scheduler-internal change independent of hardware. The Linux KPI is the capstone — it formalizes the ad-hoc `pub` API surface the subsystems build.

**Current state snapshot (Aug 2026):**
- 8259 PIC (offsets 32/33), PIT 1000Hz, single core, no per-CPU state.
- Scheduler: `SCHEDULER: SpinLock<VecDeque<Thread>>` round-robin, timer-driven preemption.
- Storage: none. Initrd is a TAR blob in HHDM. No PCI bus driver.
- Syscalls: ~35 arms, several stubs (`setpgid`, uid/gid, `getrandom`→1, fcntl `F_DUPFD` no-op).
- ACPI: bootloader already locates RSDP and passes `BootInfo.rdsp`; kernel ignores it.
- `shared::boot::mod::MMIO_DEVICE_REGIONS` already reserves LAPIC/IOAPIC/HPET phys ranges.
- Verification: `./scripts/build-kernel.sh` + `cargo test -p kernel --lib --target x86_64-unknown-none` + `./scripts/smoke.sh`.

## Phase Roadmap

### Phase 1 — Refactor (IN PROGRESS)
Scheduled in `2026-08-08-kernel-refactor-phases.md`. No new features; removes the smells the later phases would trip over (1281-line syscall fn, triplicated context switch, dead code). **Gate for everything after.**

### Phase 2 — APIC (plan: `2026-08-08-apic.md`)
Replace PIC with Local APIC + IO-APIC, migrate the timer from PIT to LAPIC timer.
- **Unlocks:** SMP (LAPIC is per-CPU; IPIs come free), finer timer, MSI later.
- **Independent of:** scheduling, storage.
- **Risk:** lowest hardware bring-up of the set — MMIO regions already mapped, IDT already dynamic.

### Phase 3 — Priority-based scheduling (plan: `2026-08-08-priority-scheduling.md`)
Replace FIFO round-robin with per-thread priority + per-queue scheduling. Modern design: CFS-like vruntime keyed runqueue, priority bands, real-time classes reserved for later.
- **Unlocks:** interactive responsiveness for shell/busybox, basis for `nice`, later real-time.
- **Independent of:** all hardware phases. Do it after APIC only because the timer tick is the preemption source and APIC timer is more precise.
- **SMP interaction:** runqueue becomes per-CPU in Phase 4; plan must isolate queue state behind an API so the per-CPU split is mechanical.

### Phase 4 — Syscall completion (plan: `2026-08-08-syscall-completion.md`)
Turn stubs into real behavior; fix inaccurate arms; grow the set toward what musl/busybox/bash need.
- **Independent of:** everything. Can land anytime; scheduled here because it also benefits from the Phase 1 split.
- **Depends on:** Phase 2 (APIC) only if it wants `clock_gettime` via LAPIC; can use PIT/TSC first.

### Phase 5 — Storage: virtio-blk → AHCI → NVMe (plan: `2026-08-08-storage-drivers.md`)
PCI enumeration first, then virtio-blk (QEMU dev/test), then AHCI (real SATA), then NVMe (modern SSD). Block layer + VFS integration.
- **Unlocks:** the Linux KPI capstone (a driver API is meaningless without real devices), persistent FS.
- **Depends on:** nothing in Phase 2–4; only the refactor. Could move earlier if a real filesystem is wanted sooner.

### Phase 6 — SMP / multi-core (plan: `2026-08-08-smp-multicore.md`)
Per-CPU data + TSS/GDT/IDT, AP boot via INIT-SIPI, IPI delivery, scheduler per-CPU runqueues, spinlock rework (no disabling interrupts that block other cores), `lazy`/`once` per-CPU safety.
- **Depends on:** Phase 2 (APIC/IPI). **Interacts with:** Phase 3 (runqueues split), Phase 5 (lock contention).
- **Highest risk in the whole roadmap** — touches every concurrency assumption in the kernel (all `SpinLock` + interrupt-disabling).

### Phase 7 — Linux KPI (capstone; complexity analysis in `docs/superpowers/plans/2026-08-08-linux-kpi-complexity.md`)
Formalize an in-kernel module/driver API (the Android-style Kernel Programming Interface): stable headers, module loading, driver registration, exported symbol tables.
- **Depends on:** all of the above. A KPI without devices (Phase 5) is academic; without SMP (Phase 6) it's single-threaded-only.

## Dependency Graph

```
Phase 1 Refactor
   ├─► Phase 2 APIC ──► Phase 6 SMP
   ├─► Phase 3 Priority scheduling ──(runqueue API)──► Phase 6
   ├─► Phase 4 Syscall completion
   └─► Phase 5 Storage (PCI → virtio → AHCI → NVMe) ──► Phase 7 Linux KPI
                                                          ▲
Phase 6 SMP ───────────────────────────────────────────────┘
```

## Parallelizability
Phases 2, 3, 4, 5 are mutually independent after Phase 1. They can be executed in parallel branches (different agents/sessions) — each has its own plan file, own files, own verification. Phases 6 and 7 are the serial bottlenecks.

## Verification gate (every phase)
```bash
./scripts/build-kernel.sh && cargo test -p kernel --lib --target x86_64-unknown-none && ./scripts/smoke.sh
```
Plus phase-specific hardware checks (e.g. APIC: verify LAPIC ID readback; SMP: `ncpu` cmdline shows 2+ cores; storage: `cat` a file from the block device).

## Explicitly out of scope (future roadmap candidates)
- User-space drivers / hardware passthrough
- Virtual memory paging to disk (needs Phase 5)
- Network stack (needs a NIC driver + PCI, Phase 5 substrate)
- Real-time scheduling classes (builds on Phase 3)
- Memory protection of kernel modules (follows Phase 7)
- Filesystem beyond the initrd TAR (needs Phase 5)
